Why a separate ai: section, and not a sentence in “custom requirements”? A sentence can only be turned into code by hand. A structured section lets the platform create the real AI objects automatically, lets the tests fake the AI's answer, and lets the preview show the feature. Free-text “custom requirements” stay for genuinely one-off things, and they can still use an AI helper: they name it in uses_ai and the hand-written task calls it (Reference A, “From a background task”).

4

The app is built: three parties, each with a clear job

PlatformBuild agent

The build agent cannot call Zango's admin API, by design. So the work is split: the platform does the fixed, repeatable setup, the build agent does the writing, and a shared runtime handles the behaviour that is the same in every app.

🛠️ Build agent writes

  • The AI's instructions (the prompts), in the right domain voice: “Use only approved answers. Say ‘unknown’ if unsure.”
  • Custom tools the AI may use, e.g. “find the MedDRA term for a symptom”.
  • Tests, one for each “how do we know it works” line.

It does not write the trigger code. That belongs to the runtime.

⚙️ Platform sets up

  • Saves the prompts in Zango (with versions).
  • Registers the tools.
  • Creates a placeholder AI account app-llm (service and model from the blueprint, no key yet) if there isn't one already.
  • Creates every AI agent in Zango on that account: model, output format, tools, memory. They're all visible in the console from the first build.

📦 Runtime handles

  • Running the AI at the right moment (button, new record, status change, schedule).
  • Sending only the allowed fields.
  • Holding a suggestion until someone accepts it.
  • Showing “AI isn't connected yet” instead of breaking. Saving the record always works.

The order things happen in

  1. The platform checks the blueprint and makes a to-do list. There is one “write the instructions” item per AI helper.Platform
  2. The platform copies in the shared runtime, which now includes AI.Platform
  3. The build agent writes the app's code, plus the prompts and tools for each AI helper.Build agent
  4. The platform runs setup: database, roles, then the new “AI” step. It creates the placeholder account (first build only), then the prompts, tools and agents, all linked to that account.Platform
  5. If the placeholder has no key yet, the build carries on and only pauses at the very end, in Step 5.Platform
Under the hood · files and the new setup step
  • Checker zango-app-studio/scripts/spec_check.py: resolves ai into spec.resolved.json, creates holes of kind ai_prompt (writes backend/<module>/ai/<code>.system.md and .user.md) and ai_tool (writes tools.py). --audit-holes checks that prompts use only declared {{variables}}. A custom requirement with uses_ai gets its hole brief extended with the agent's inputs and output, and the audit fails if the hole never calls each listed agent.
  • Runtime assets/backend/zas_core/ai.py: run(agent, obj, trigger, …), a Celery task zas_ai_run, models ZasAiRun and ZasAiSuggestion, role-checked endpoints, built-in tools zas_read_record and zas_search_records (scoped to the acting user), and a fake mode for tests.   • Frontend runtime assets/frontend/zas/ai/: AiButton, AiSuggestionCard, AiChatPanel, AiFormAssist, AiStatusPill.

Connect an AI account: the only step where you act

You

The build has already created a placeholder AI account called app-llm, and every AI helper is already set up on it. All that's missing is the key. You fill in the placeholder once: paste a key, and optionally switch the service (Anthropic, OpenAI, Azure OpenAI, AWS Bedrock) or the model. Nobody else (no AI, no chat, no log) ever sees the key. It is stored encrypted, inside this one app.

The placeholder account, start to finish
  1. Build creates it: app-llm · Anthropic · claude-sonnet-4-5 · Needs a key. All AI helpers are created and linked to it.Platform
  2. The console shows everything right away: App → AI lists the account and every helper (“Waiting for key”). You can already review prompts, tools and settings.You
  3. You fill it in: paste the key. You can also switch the service (say Anthropic → Azure OpenAI) and pick the model. The key is checked live before it's saved.You
  4. Every helper follows: they're linked to the same account, so they start working straight away, without a rebuild. If you switched service, helpers still on the old default model move to the new one.Platform
  5. Fine-tune any helper: App → AI → Agents. Change one helper's model, creativity or length, or move it to a second account. Later rebuilds never undo these changes.You
Three moments; you need only one
  1. Early (optional): while reviewing the blueprint, click “Connect AI account”. The AI then gets tested for real in the first build.
  2. During the build (most common): the build finishes everything else, then pauses with a card: “Connect an AI account to finish testing the AI features.” You either connect or press Finish without it.
  3. Any time later: App → AI → Providers → app-llm → Add key. The app's AI switches on as soon as the key checks out.
A missing key never fails the buildEverything else is built and tested. The AI features just say “not connected yet” until you add one.

What “Finish without it” does

Right away
  • The build finishes as done, not failed. Only the real AI check is skipped, and the report says so.
  • Nothing is skipped in setup. The placeholder account and every AI helper were already created in Step 4, before this pause. They stay in Zango, waiting for a key, and nothing needs rebuilding later.
  • The next build won't pause again for this. The choice is remembered per app, unless the blueprint adds new AI helpers.
For app users, until a key is added
  • Records save normally. AI never blocks the work.
  • AI buttons are greyed out: “AI isn't set up for this app yet.”
  • Automatic AI runs are skipped and logged. AI fields stay empty, so people fill them in by hand.
  • After a key is added, missed runs are not replayed automatically (that could mean surprise cost or overwritten values). Press ✦ on a record to run it there.
Under the hood · placeholder provider: what has to change in Zango

Why the platform has to create the placeholder itself, from today's code:

  • AgentCreateSerializer.validate (api/platform/ai/v1/serializers.py:768) requires an existing, enabled provider_id, so agents can't be created without a provider.
  • AppLLMProviderCreateSerializer.validate (:133) checks the key live, so POST /ai/providers/ can't create a keyless placeholder. The platform creates it through the ORM instead.
  • AppLLMProviderUpdateSerializer (:227) can't change provider_slug, doesn't re-check a new key, and leaves is_validated as it was. So filling in the placeholder needs a new action.

Changes:

  • Model apps/ai/models/provider.py: add is_placeholder = BooleanField(default=False), with a tenant migration in apps/ai.
  • New endpoint POST /ai/providers/<id>/connect/ with {provider_slug, config, default_model, fetched_models?}. It reuses the create serializer's checks (required config fields and a live key check), then replaces config_encrypted, may change provider_slug, rebuilds enabled_models, and sets is_validated=True and is_placeholder=False. If the service changed, any agent still on the old default_model moves to the new default. Agents the user set to another model are left alone.
  • Core guard ai/agent_client.py run(): if the provider is a placeholder or not validated, raise a new ProviderNotConnected(ZangoAIError) before any LLM call, so no failed invocation rows pile up. zas_core.ai turns it into the “unavailable” state. Hand-written get_agent() code gets a clear error too.
  • Agent test button: AgentTestViewAPIV1 returns “Add a key to app-llm first” for placeholder providers.
  • Console: a placeholder card in Providers (“Needs a key · created by App Studio”) with Add key, which opens ProviderDrawer in connect mode. Agents show “Waiting for key”.
  • Ownership on rebuild: the AI step sets provider, model, temperature and max_tokens only when it first creates an agent. After that they belong to the user. The build only updates output schema, tools, memory, description and prompts (when their text changed).
  • Remembered skip: .zas/ai_state.json records provider_skipped_for: [agent codes]. The pause only comes back for agents not in that list.
Under the hood · the build pause
  • New pending action kind connect_ai_provider in studio_build.py::environment_actions(). It blocks only the live AI test layer, and uses the same pause and continue flow as install_playwright (AgentRun.pause → WAITING → /continue/).
  • still_failing(): provider app-llm has is_placeholder=False, is_enabled and is_validated. Otherwise /continue/ returns 409. skip=true finishes without it, and the test is reported as skipped, never passed.
  • The drawer uses GET /ai/providers/available/ (form fields per service), POST /ai/providers/fetch-models/ and the new POST …/connect/.
  • The key never enters the build run or its transcript. credentials.redact() also masks sk-ant-… and sk-… patterns as a backstop.
  • Later idea, not in this plan: a workspace-wide AI account (one key for every app). It's convenient in dev, but it mixes costs and data between apps, so it would be opt-in.

The AI is tested, cheaply and reliably

Platform

AI gives slightly different answers every time, and every call costs money. So almost all tests use a stand-in AI that returns the blueprint's sample answer. Only one small real call per helper checks that the real thing works.

Tests with the stand-in AI (free, always run)
  • Only the right roles see the AI button and can accept a suggestion.
  • A suggestion changes nothing until someone accepts it.
  • Each “how we know it works” line from the blueprint passes.
  • With no AI account, the app shows “not connected” and still saves records.
  • The AI can't trigger itself in a loop.
One real check per helper (needs Step 5)
  • One real run per AI helper on a sample record.
  • Checks that the answer has the right shape, and records time and cost.
  • Capped at about $0.50 per build.
  • No account connected → reported as skipped.

The build report gets an “AI helpers” section: each helper, when it runs, whether a person checks it, the real-test result and the cost.

Under the hood
  • Fake mode: with ZAS_AI_FAKE=1, zas_core.ai.run returns preview.sample or a fixture override (ctx.ai_fake(agent, payload)).
  • Layers: zas_test.api (permissions, loop guard, unavailable state), zas_test.ui (buttons and cards per role), zas_test.scenarios (acceptance), and a new ai_live layer.
  • Report: zas_test/report.py and references/report.md. Show progress, not failure details, to app creators.

The AI at work inside the finished app

App user

For the person using the app, AI shows up as a button, a suggestion to accept, a filled-in form or a chat panel. Every AI-written value carries a small ✦ AI mark.

One request's day, in the example app
  1. Dr Rao's question arrives and a new request is created. In the background, the AI suggests the topic “Safety” and flags “possible side effect”.automatic
  2. The MI specialist opens the request and sees the suggestion card. They click Accept, and the values are saved with the ✦ AI mark and their name as the person who accepted.specialist
  3. They move it to “Start response”. The AI drafts the reply from approved answers.automatic
  4. They edit the draft, or click ✦ Redraft.specialist
  5. The medical reviewer approves, which is the existing human step. The AI never sends anything itself.reviewer
Safety rules built in The AI only sees the fields the blueprint lists, and only the records the user could already see. By default, anything it writes needs a person to accept it. If the account is missing or over budget, users see “AI unavailable right now” and keep working.

How the result comes back: shared runtime, not per-app code

Where it runsTriggersHow the result comes back
Celery (task zas_ai_run)create / update / delete, transition, tag, schedule, buttonA ZasAiRun row moves through queued → running → done | failed | unavailable. The result is written to the record (review: none) or stored as a ZasAiSuggestion (review: suggest). On screen, AiStatusPill / AiButton poll GET …/zas/ai/runs/<id>/ every 2s (backing off, stopping at done/failed), then show the suggestion card or refresh the record. The save is never blocked.
Inside the request (no Celery)form_assist, chatThe user is waiting at the screen, so the endpoint calls the agent directly and returns the answer, with the agent's timeout_seconds as the limit. Still logged as a ZasAiRun. Chat streaming is an open decision (Reference D).
Inside your own tasktaskrun_from_code() is synchronous within the Celery worker that is already running the custom task, so the code gets the result back directly. Nothing to poll.

The build agent writes none of this: queueing, status rows, polling, retries and the "unavailable" state live in zas_core/ai.py and src/zas/ai/, which the platform copies into every app. The build agent only writes prompts, custom tools and uses_ai task code. Per-agent run: async|inline can override the default (for example, an inline button for a 2-second classification).

Note that the Zango docs say triggered_by="task", but the code's values are user · celery · cron · system. Follow the code.

D · Risks, and decisions for you

Risks we're managing
  • Patient data going to an AI company. Guardrails don't exist yet. For now, the control is that each helper sends only the fields listed in the blueprint, and the review panel shows those fields.
  • Surprise cost. Controlled with a monthly budget per account, a loop guard, a daily run cap per helper, and spend shown on the Overview.
  • AI seeing records the user can't. The AI's tools act with the user's own access. A test proves it.
  • Flaky AI tests. Handled by the stand-in AI. The single real check warns but never fails the build.
