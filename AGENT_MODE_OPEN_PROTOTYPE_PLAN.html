Agent Mode · Requirement phase · Spec & plan

Open Prototype: any HTML in the requirement phase, still mapped to the YAML

Today the requirement agent edits only the YAML, and one fixed page in one design system draws the preview from it. This plan lets the user chat their way to a full HTML prototype of any shape, at the level of the Sponsorships app, while the agent keeps the YAML in step through an explicit map. File upload in chat is a secondary path, for references and existing HTML.

Branch feat/agent-mode-app-studio-skill Date 23 Oct 2026 Status v5 · P1 + HTML import done · Stage 2 next Scope Stage 1 requirement agent, Stage 2 build agent
Generated in chat

The agent writes the prototype in parts (tokens, shell, data, one file per screen), assembled into one HTML. The shell and home appear in minutes; the other screens fill in, in parallel.

Two artifacts, one map

prototype.html holds the look and the flows; app_spec.yaml holds what gets built. data-zas-* markers tie them together, and a map check blocks "ready" on drift.

Uploads, later

Images, pasted screenshots, documents and HTML in chat replies. They serve as references, or as a starting prototype.

3Options considered

A · Widen sketches small

Keep the YAML-drawn page. Run each sketch in its own iframe with scripts, and add free tokens to app.design.

  • Lists, forms and the shell keep the kit's look
  • The user still can't reshape the whole app (nav, login, home)

Doesn't meet the goal.

B · Prototype only medium

The agent writes HTML. The YAML is extracted from it later, at approval.

  • Total freedom
  • Structure goes unchecked during the chat; extraction at the end is lossy and surprises the user
  • Loses validation, open decisions and contracts

Too risky for the build.

C · Two artifacts, one map recommended

The prototype owns the look and the flows. The YAML owns the structure. The agent edits both in the same turn, and a map check keeps them in step.

  • Any HTML, with the spec, validation and gates kept
  • Drift is caught on every edit, not at the end
  • The current renderer stays as the "kit" mode

Meets the goal without losing what part 1 built.

Proposed decision

Build option C as a new requirement mode, preview_mode: "open", behind AGENT_MODE_OPEN_PROTOTYPE and a "Free design" toggle on intake. Existing requirements stay on "kit".

4Generating in chat

The main path is a conversation that ends in a Sponsorships-level prototype, with no upload. That shapes four things the first draft of this plan underestimated.

4.1 Size: the prototype is written in parts

Sponsorships is 237 KB, about 60–65k output tokens. At a typical 50–80 tokens a second, that's 15–20 minutes of pure writing (an estimate). Analyst turns are capped at 600 s (views.py L833), and one tool call that large is fragile. So the agent never writes the whole file. It writes parts, and the server assembles them:

proto/
  manifest.json       screens, roles, libraries            # drives probe, Point, map
  tokens.css          palette, type, radii, shadows        # the agent's own design
  app.css             components and layout
  data.js             sample records, personas, dates
  shell.js            nav, header, persona switch, router
  screens/home.js     one file per screen: render + its handlers
  screens/requests.js
  screens/request.view.js
  …
  • Edits stay small. "Make the request header gold" touches one 8 KB part, not 237 KB.
  • Screens can be written in parallel by sub-agents (§9, P1).
  • The preview reloads after each part, so the user watches the app appear.
  • The build bundle (B1) gets one file per screen for free.

4.2 Progressive first draft

4.3 A starter, not a design system

Every app like Sponsorships has the same plumbing: a router, a persona switch, a data store, data-act click delegation, icons, and helpers for pills, tables, drawers, tabs, toasts and forms. A starter of about 25 KB in the pack provides this. Its CSS is a neutral token skeleton that the agent replaces. The agent may restyle, replace or ignore any of it. The starter only saves writing and prevents common bugs; it puts no limit on the look.

4.4 Design guidance for the agent

A new prototype-design skill for the analyst, modelled on the guidance that produced Sponsorships:

  • A look derived from the subject, with its own tokens per app. No house look is imposed, and the generic defaults (one gray, one brand hue) are avoided.
  • Information design for working tools: summary before detail, state shown in form (pills, stripes), a home screen per persona with "your work".
  • Realistic sample data in the domain's own units, names and dates. No lorem ipsum.
  • Every state drawn: empty, pending, rejected, overdue, permission-denied.
  • Two worked examples we write ourselves for the pack, in fictional domains (for example lab sample tracking and field expense claims), split into parts. They show the quality bar without copying any user's file.

5Design

5.1 The prototype artifact

  • Parts, assembled into one HTML file. Parts are stored per requirement (§9, P1 data model). The assembled file is what the frame, the probe and the build see. A version freezes the spec and the parts together under one prototype_hash. Cap: 2 MB assembled, 150 KB per part.
  • No design rules. Any CSS, inline scripts, Google Fonts, and scripts from cdnjs, jsdelivr and unpkg (pinned versions). Nothing else from the network.
  • Required: a manifest. One small JSON part (assembled as a <script type="application/json"> block) that lets the probe, Point and the map check drive the prototype: 
    <!-- in the assembled prototype.html -->
<script type="application/json" id="zas-proto">{
  "screens": [
    {"id": "requests",      "title": "Sponsorship requests", "roles": ["office","requester"]},
    {"id": "request.view",  "title": "Request",              "record": "sponsorship_request"},
    {"id": "signin",        "title": "Sign in",              "only": "prototype"}
  ],
  "roles": {"office": "Sponsorship Office", "requester": "Requester", "compliance": "Compliance"}
}</script>
<script>ZAS.ready({ go: (screen, {role, record}) => render(screen, role, record) })</script>

5.2 The runtime shim, zas-proto.js

The console injects the shim before the prototype's own scripts. It replaces adapter.js for open mode.

  • ZAS.ready({go}) registers the prototype's navigator. ZAS.at(screen, {role, record}) reports where the user is, replacing ZAS_LOCATION.
  • ZAS.store is an in-memory key/value store per preview session, seeded from the prototype's own sample data. ZAS.files is an in-memory file store, so evidence uploads work in the preview.
  • window.claude.use('db'|'assets') is the same pair under the name Claude artifacts use. Imported artifacts like Sponsorships run without changes.
  • A persona bar from manifest.roles switches role by calling go. The prototype may also draw its own.
  • Point mode (see 5.4) and a zas:error relay for uncaught errors, which feed the probe.

5.3 Rendering and isolation

  • The prototype gets its own <iframe srcdoc> with sandbox="allow-scripts allow-popups allow-forms". No allow-same-origin means no access to console cookies or APIs. This matches EmbeddedBuilder.tsx L148–153, minus allow-modals.
  • CSP on the srcdoc via a <meta> tag: script-src 'unsafe-inline' cdnjs jsdelivr unpkg, style-src 'unsafe-inline' fonts.googleapis.com, font-src fonts.gstatic.com data:, img-src data: blob:, connect-src 'none'. The direct-open route in app_templates/v1/views.py L197 gets the same policy as a header.
  • The probe worker allows the same hosts (FONT_HOSTS becomes PROTO_HOSTS), so screenshots match what the user sees. The kill-after-30 s rule stays.
  • The full-page tab (PreviewTabPage) renders the same frame. BroadcastChannel pointing carries over.

5.4 Point and edit, for any element

The user should be able to point at anything, not only at mapped parts. In point mode the shim captures the click and sends:

{ "screen": "request.view", "role": "compliance", "record": "SP-0142",
  "ref": "/modules/@sponsorship/entities/@request/fields/@amount",   // nearest data-zas-ref, if any
  "anchor": "#req-head .kpi:nth-child(2)",                           // stable CSS path
  "text": "Amount  $42,000", "html": "<div class=\"kpi\">…</div>" }   // trimmed to 600 chars

clean_focus learns these fields, and focus_note renders them as [Preview: Request (Compliance) · Amount field · #req-head .kpi:nth-child(2)]. The agent can then proto_find the snippet and patch it.

5.6 What changes in the YAML

The structure of the spec does not change. Two additions record what the build needs from the prototype:

app:
  theme: { primary: "#458261", secondary: "#B58812" }   # unchanged, kept for kit mode and fallbacks
  design:                                            # new, open mode only; free-form tokens
    source: prototype
    fonts: { body: Inter, mono: JetBrains Mono }
    tokens: { brand: "#458261", accent: "#B58812", surface-page: "#F7F7FA", r: 10px, ... }
prototype:                                           # new; written by the tools, not by hand
  hash: 9f2c…                                         # ties this spec version to the file
  screens:
    - { id: requests,     maps: /pages/@requests }
    - { id: request.view, maps: /detail_views/@sponsorship_request }
    - { id: home,         maps: /pages/@home }          # a dashboard or custom page
    - { id: signin,       only: prototype, why: "Platform sign-in is used in the app" }

schema.json gains app.design (free tokens object, fonts with string values) and a top-level prototype, both optional. In open mode, the SCHEMA.md line "Anything more (fonts, layouts) is not offered" is replaced by "the look lives in the prototype; record its tokens in app.design".

Custom pages in open mode don't need a preview: sketch. Their screen in the prototype is the sketch, so the UNSKETCHED_RULES gate checks for a mapped prototype screen instead. Contracts (data, acceptance) are still required.

5.7 Prompt and guidance

  • New pack doc PROTOTYPE.md, read in open mode in place of the kit parts of SPEC_EXTENSIONS.md §2. It covers the manifest, the refs, the shim, patch-don't-rewrite, and "one turn = prototype and spec together".
  • DRAFTING.md: the ladder stays for behaviour, so CRUD and workflow are still preferred over custom logic. It no longer governs look: any screen may be designed freely as long as it maps to a declared page.
  • _PREVIEW_TOOLS_APPEND becomes mode-aware, with the open-mode gates from §6.
  • Design quality: the analyst may load the pharma-enterprise-ui values (tokens, treatments) as a starting palette when the user gives no direction. That is a default, not a rule.

6The map contract

This is the part that keeps "any HTML" buildable. The prototype marks the elements that correspond to the spec. The map check runs every screen for every role headlessly, collects the marks, and resolves them against the YAML.

AttributeOnResolves to
data-zas-screen="requests"A screen's rootA manifest screen, then prototype.screens[].maps
data-zas-ref="/modules/@m/entities/@e/fields/@f"Columns, fields, facts, filters, KPIsAny spec-tool path, same grammar as today's data-zas-path
data-zas-action="transition:approve"ButtonsA workflow transition (or create:<entity>, req:<code> for a custom requirement)
data-zas-only="prototype"AnythingDeclared as a mock, so it is excluded from both checks

Map report, after every write to either side

Map: 11/13 screens mapped · 1 prototype-only · 1 unmapped
✗ screen "agents" has no spec page            → add a page or mark it only: prototype
⚠ /modules/@sponsorship/entities/@request/fields/@cost_centre  is in the spec, shown nowhere
⚠ transition "send_back" (office) has no button in screen "request.view"
✗ data-zas-ref "/modules/@sponsorship/entities/@request/fields/@budget" does not resolve

Gates in spec_mark_ready (open mode)

  1. Every manifest screen draws for each of its roles with no uncaught error and no blank screen.
  2. Every screen is mapped to a spec page or declared only: prototype with a reason.
  3. No data-zas-ref or data-zas-action fails to resolve.
  4. Every workflow transition has a button somewhere for its role. Every entity field is shown somewhere, or listed in the warnings the user sees at approval.
  5. Each changed screen was looked at once since it changed (the existing sketch_looks, keyed by screen id + prototype hash).
  6. prototype.hash in the YAML equals the stored file's hash. The tools keep it in step, so a mismatch means a bug.

The server approval gate (approval_problem() → 409) re-checks points 2, 3 and 6 without a browser, using a static parse of the refs. Points 1, 4 and 5 stay in spec_mark_ready, as today.

9Build plan

Generating in chat comes first: P1 is the whole generation loop, and it can be used on its own. P2 and P3 make it safe to build from. Uploads follow as an extra path. Each phase lands behind AGENT_MODE_OPEN_PROTOTYPE and the "Free design" toggle, and leaves kit mode untouched.

P1

Generate the prototype in chat

backendconsolepack + skill~6–7 days

Outcome for the user. With "Free design" on, a user describes their process in chat. Within about 3 minutes of answering the interview they see a working shell in an app-specific look. Within about 15 minutes they have every screen, with personas, sample data and working flows. Later messages change exactly what they ask for.

P1.2 Assembly, agent_mode/prototype.py (new)

  • assemble(parts) → (html, problems) is deterministic. The order is:
    1. <meta> CSP;
    2. Google Fonts links from the manifest;
    3. tokens.css, app.css, then screens/*.css;
    4. manifest JSON;
    5. zas-proto.js shim and starter;
    6. library <script src> tags from manifest.libraries;
    7. data.js, shell.js, then screens/*.js in manifest order;
    8. ZAS.boot().
  • Each part's JS runs in its own try, so one broken screen doesn't blank the app. The error is reported with the part's name.
  • Static checks at assembly:
    • valid manifest JSON;
    • each manifest screen has a part, and each screen part is in the manifest;
    • library URLs only from cdnjs, jsdelivr or unpkg, with a pinned version;
    • size caps;
    • new Function parse of each JS part, so syntax errors surface before the frame loads.
  • Route GET requirements/<uuid>/prototype/ returns the assembled HTML with the same CSP as a header and an ETag of the hash. ?v=<version> returns a frozen version.

P1.3 Tools on SpecWorkbench

The tools from §5.5 are proto_outline, proto_write, proto_patch, proto_read, proto_find, proto_remove and proto_rename. They are registered only when preview_mode == "open".

  • Every write reassembles the prototype, saves the parts, bumps prototype_revision, and returns a short result: the part's size, total size, any assembly problems, and screens added or removed.
  • In P2, the map report is appended to this result.
  • Writes are serialised per requirement with a row lock, because screen writers run in parallel.

P1.4 Parallel screen writers

  • build_analyst_options registers a screen-writer sub-agent through the SDK's agents option, and adds Task to the analyst's tools in open mode only.
  • The writer gets proto_read, proto_write, proto_patch, Read (pack and skill files), and the prototype-design skill. It has no spec tools, so only the analyst writes the YAML.
  • The brief per screen covers: screen id, purpose, personas, which records and fields, actions and their outcomes, tokens and helpers to use, and the parts it may touch (screens/<id>.* only).
  • Spike, day 1: confirm that in-process SDK MCP tools reach Task sub-agents, the way PreToolUse hooks were confirmed for 0.2.152. If not, the fallback is sequential writing in the analyst's own loop, with a longer first turn.

P1.9 Tests
