Preview-to-Spec Plan

Part 1 built (A–D) · updated 15 Oct 2026 Branch feat/agent-mode-app-studio-skill Template zango-app/1

How the requirements analyst should see the App Studio preview, and how every change a user asks for, on the frontend or the backend, should be recorded in app_spec.yaml. The goal is a spec the build can turn into a high-quality app, using as much of the CRUD and workflow runtime as possible.

The plan in three moves
  1. Keep the YAML as the only thing that changes. The preview stays a pure function of the spec. Every visible change is a YAML change; nobody edits HTML.
  2. Make YAML say more, in order. A five-level ladder from theme tokens to custom code. The analyst always uses the lowest level that expresses the request, and anything custom carries a structured contract instead of prose alone.
  3. Give the analyst eyes, for custom screens only. The declarative parts render the same way every time from the YAML, so validation is enough there. For custom screens, the analyst checks its own sketch in three steps, cheapest first: run it, read a text summary of what it drew, and take a screenshot of that one screen only when the question is visual. It also learns which element the user is pointing at.
Progress, 15 Oct. Phases A–D are built and tested (588 tests; the only failures are the 8 existing test_skill_plugin developer-server ones), and Point was tested live in Chrome. Template zango-app is at 1.1.15. Phase E, the approval bundle, is next and opens part 2. See What testing changed for the fixes made after the first real analyst turns.

The gap. The user judges the app by the preview, but the analyst writes it blind and the build ignores a large part of it. Custom screens are the worst case: a JS sketch that only the user has seen, plus a paragraph of prose.

Principles

  • One source of truth. app_spec.yaml is the requirement. The preview is derived from it and is never edited. Anything the user approves must be reconstructible from the YAML and the seeded demo data.
  • Declarative first. Each request is expressed at the lowest level of the ladder that can hold it. A declared element is something the runtime builds deterministically and tests by machine; a custom one is code the build agent writes and we hope is right.
  • Custom is a contract, not a paragraph. When something has to be custom, the YAML records its data, interactions, states and acceptance criteria in structured keys, with the sketch as a visual reference.
  • The analyst checks its own work. No turn ends with a preview the analyst hasn’t verified renders for every role it touched.
  • Same vocabulary on both sides. Every new YAML key has a renderer in app-studio.html and a counterpart in the App Studio runtime, or it doesn’t ship. The preview must never promise what the build can’t make.

The ladder

Every change a user asks for lands on one of five levels. The analyst starts at the bottom and moves up only when the level below cannot express the request. The panel reports how much of the app sits at each level, so “mostly declarative” is visible and measurable.

The rule for moving up. Before writing an L3 screen, the analyst checks for an L2 equivalent. A screen that reads one entity and shows it as a table, list, board or calendar is a view, not a custom page. A screen made only of KPIs, bar charts and record lists is a dashboard. A lint (rules.json) warns when a preview sketch only uses ctx.ui blocks that have a declarative form.

Why dashboards move to L2

Most custom pages in drafted specs are dashboards, and they are already composed from ctx.ui.kpis, bars, list, table and board. Those calls map one-to-one onto runtime components (StatTile, Panel, ZasTable). Expressing the same tree as YAML blocks lets the preview draw it without JavaScript and lets the build generate it instead of rewriting it from prose. The value grammar is the one 360 stats already use (count, sum, where).

Giving the analyst eyes

Only custom screens need it. Everything at L0–L2 is drawn by app-studio.html the same way every time from the YAML. If spec_validate passes, it renders, and a screenshot would cost tokens and catch nothing. The analyst writes the preview JavaScript of each L3 screen, and today it never sees what that code produces. That is what needs eyes.

How UI agents usually check their work

Agents that build UI with a browser check in layers, cheapest first: run the code and catch errors, then read the page as structured text (Microsoft’s Playwright MCP reads pages through the accessibility tree by default, not pixels), and take a screenshot only when the question is visual. The user, who is already looking at the preview, stays the final judge.

Three steps, cheapest first

StepWhenWhat the analyst getsCost
1. Run the sketchAutomatically, after every change that adds or edits a custom page, tab or panel, for every role that can see itErrors with their message; empty output; entities read with ctx.rows that have no demo rows for that role; unknown field keysNearly free
2. Text summary of what it drewSame; appended to the tool resultAn outline of the output: “4 KPI tiles: Open 12, Overdue 3, …; bars ‘Open by status’ with 5 bars; list ‘Due soonest’, 8 rows; one panel empty”A few hundred tokens
3. Screenshot of that screenOnly on request: a new custom screen, a visual complaint from the user, a mockup to match, and once per screen before readyAn image of that component only (element-level, not the whole page), at 1280 or 390 px~1.5k tokens

Steps 1 and 2 catch the common failures: a broken sketch, wrong field names, nothing showing for a role. Step 3 answers what only an image can: does it read as a board, is it cramped, does it look like their mockup?

And what the user points at

With each chat message, the console sends where the user is in the preview (role, page, record, tab) and, if they used “point at this”, the element’s data-zas key and its spec path. This works on every page, declarative or custom, and costs nothing: “make this bigger” and “this number is wrong” arrive already tied to a place in the YAML.

How it is built

  • One renderer. The headless run loads the same app-studio.html and adapter.js as the console, in Playwright’s Chromium (already in base.txt). There is never a second preview implementation to drift.
  • Protocol zango-builder/2. It adds a run_sketch message {screen, role, id} that returns the errors and the summary, a goto message for screenshots, and data-zas attributes with spec paths on rendered elements. Those attributes also serve the user’s “point at this” and the build’s preview parity check.
  • The summary comes from ctx.ui. Each kit call (kpis, bars, list, …) records what it drew, so the outline is exact. Hand-written markup is summarised from its text and element counts.
  • Sealed. All network requests are blocked and there is no storage. Sketch code from the analyst runs only against the seeded demo data, with a time limit per run.
  • Warm and lazy. The browser starts on the first custom screen and is reused for the rest of the session. A spec with no custom screens never starts one. The MCP server is in-process and async, so it uses Playwright’s async API.

Preview in a new tab

The preview beside the chat is narrow. The user should be able to open it in its own browser tab, to click through the app at full width, look at it on a second screen, or share it with a colleague who can open the console.

  • An “Open in new tab” button on the preview header in the console. The tab opens at the same role, page, record and tab the user was looking at, using the goto deep link from phase A.
  • Its own console page, for example /requirements/<id>/preview. It loads the same app-studio.html and adapter.js in the same sandboxed iframe, fetches the current spec from the API with the user’s session, and checks the same permission as the requirement itself. There is no public link.
  • Live. The tab subscribes to the same spec event stream as the chat, so every change the analyst makes redraws it, keeping the user’s place when the page still exists.
  • Read-only, like the embedded preview, with the role switcher. A small bar says which requirement and spec version it shows, and when it is out of date because the stream dropped.
  • Pointing still works. “Point at this” in the tab sends the focus to the chat of that requirement, so the user can comment from the full-size view.
  • After approval the tab shows the approved version and says so, so nobody mistakes a later draft for what was signed off.

How changes land in YAML

All additions are optional keys on zango-app/1, so existing specs stay valid. Each goes into SCHEMA.md, schema.json, the preview renderer and the build’s spec_check.py together.

L0 app.ui: the look, as choices

Fixed choices, each mapped to a set of token values in tokens.css and in the preview. No free CSS, no colour literals beyond the brand colours.

# app
app:
  theme: { primary: "#3B3FB6", secondary: "#0E7490" }
  ui:
    density: comfortable      # compact | comfortable
    radius: rounded           # sharp | rounded | soft
    nav: sidebar              # sidebar | topbar
    headings: sans            # sans | serif

L2 Dashboards as blocks

pages:
  - code: ops_home
    type: dashboard
    title: Operations
    route: /app/home
    roles: [Manager]
    blocks:
      - kpis:
          - { label: Open tasks, value: { count: task, where: "status not_in [done]" }, icon: list-checks, go: tasks }
          - { label: Overdue, value: { count: task, where: "status not_in [done] and due_date < today" }, tone: red }
      - grid:
          - bars: { title: Open by status, entity: task, group_by: status, where: "status not_in [done]" }
          - list: { title: Due soonest, entity: task, where: "status not_in [done]", sort: due_date,
                    primary: title, meta: due_date, limit: 8, go: task_360 }

Every block honours the role’s access and row scoping, exactly as a list page does. Block types: kpis, bars, list, table, board, grid, stack, panel. Anything else makes the page custom.

L3 A custom screen with a contract

The prose text stays. Around it, structured keys say what the build must deliver and how the build can check it. The preview sketch is the visual reference the user approved.

  - code: workload
    type: custom
    title: Team workload
    route: /app/workload
    component: WorkloadBoard
    roles: [Manager]
    text: >-
      One column per active team member with their open tasks, ordered by due date.
      Overdue tasks are highlighted. Drag a task to another person to reassign it.
    data:                                     # what it reads, always role-scoped
      - { entity: team_member, where: "is_active == true" }
      - { entity: task, where: "status not_in [done]" }
    interactions:                             # what it does, in runtime terms where possible
      - { on: card_click, go: task_360 }
      - { on: drag_card, update: { entity: task, field: assignee }, roles: [Manager] }
    states:
      empty: No open tasks. Everyone is clear.
    acceptance:                               # testable, in the user's words
      - A manager sees one column per active team member.
      - A task past its due date shows its date in red.
      - Dragging a task to another column reassigns it and the 360 timeline records the change.
    refs: ["doc:2#p3"]                        # an uploaded mockup or document page, if any
    preview: |
      const { ui } = ctx; …

A custom tab or sidebar panel on a 360 page takes the same keys, with data paths relative to the hero (via).

L4 Typed custom logic

modules:
  - code: vendors
    custom_requirements:
      - code: notify_on_approval
        area: notification          # notification | integration | computation | scheduled | rule | report
        trigger: { entity: vendor, on: transition, transition: approve }
        text: Email the vendor's primary contact that they are approved, with their vendor reference.
        acceptance:
          - Approving a vendor sends one email to the primary contact.
          - The email contains the vendor reference.
        preview: { toast: "Email to the primary contact (simulated)" }

area and trigger tell the build which hole kind and signature to use (custom-code.md), so it doesn’t have to guess from prose. The optional preview.toast lets the preview show the side effect when the user runs the transition, so they see the email happen.

What stays out of the spec

  • Why something changed (which message, which flag) goes in a sidecar decision log next to the existing flags, keyed by spec path. The YAML holds the requirement, not its history.
  • Screenshots are never stored in the YAML. They are derived and can always be rendered again from it.
  • Free CSS or HTML is never stored. Pure appearance is app.ui; anything structural is a key or an L3 contract.

Hand-off to part 2

Part 2 will design how all of this reaches the build agent. Part 1 sets it up so that, at approval, the platform can freeze an approval bundle next to the spec:

  • the approved YAML;
  • for each role × page (and the first record of each 360), the element tree, which is text and cheap;
  • for each L3 screen, its contract, its text summary and a screenshot per role;
  • the user’s reference uploads named in refs.

The element trees switch on the build’s preview parity check, which is skipped today, for the declarative pages. The screenshots give the build agent the visual target for the custom screens, where it actually writes UI. The details are part 2.

Questions (answered 15 Oct)

  1. app.ui scope. Are density, radius, navigation style and headings the right first set, or do you want fewer knobs (brand colours only) to keep apps consistent? Answer: radius and density only.
  2. Dashboards. A new type: dashboard page, or blocks allowed on type: custom with component left out? Answer: a new type: dashboard.
  3. Reference uploads. Should users be able to upload screenshots of an existing system during the requirement phase, for refs and preview_compare? Answer: skipped for now.
  4. Show the user what the analyst saw? For example, attach the analyst’s screenshot to its reply when it changed a screen. Open. The analyst now gets one automatically; showing it to the user is not built.
  5. Custom budget. Should the share of L3 and L4 items only be reported, or should a limit trigger a confirmation (“this adds 3 custom screens; the build takes longer”)? Answer: count only, shown as a pill in the preview header.
