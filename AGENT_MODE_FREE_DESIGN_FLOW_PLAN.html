Implementation plan · Agent Mode

Free design build flow: spec + mockup → kit → slices

Harsh Shah · 2026-10-27 · Draft · branch feat/agent-mode-open-prototype

Overview

Default design works because every spec element maps to a known kit component. Free design has no such mapping: the build agent redraws arbitrary HTML into React freehand, in one long pass, without running it. The zango_isn_hcp build (2 runs, 160 turns, about $25) showed every failure this causes: 20 of 24 reference screens captured blank, 9 admin screens forced onto the standard page, the custom pages returning HTTP 500, and design parity reporting 0% difference between a blank reference and an error page. Create case was blocked by platform bugs the agent could not fix.

The new flow follows the industry pattern for spec-driven builds (Spec Kit, Kiro: gated phases, small testable tasks; Figma Code Connect: map design to components before writing code; agents check their own screens before saying done).

Analyst: YAML (+ screen links) + mockup ── mockup check gate ──▶ creator approves (the only approval)
   ▼
Build:  kit from mockup ── automatic diff gate (no approval) ──▶ slice 1 (hero record) ─ verify ─▶ slice 2 … ─▶ final verify
   ▼
Failures: app code → agent · platform/test code → us · same failure twice → stop

The YAML stays the spec. Without a mockup, the kit phase is skipped and the default kit is used, so the default path is unchanged apart from building in slices.

Steps

Phase A: unblock (platform bugs found in the build)
  1. A1. Field-vs-field rules on formszas_core/expr.py:526 resolves the right-hand word (bp_systolic > bp_diastolic) only when the record has _meta. _FormRecord (mixins.py:60) has none, so every such rule fails on every create form. Fix: _FormRecord takes the form's model and exposes _meta, or _operand checks the record's values first. Then remove the class-swap workaround from zango_isn_hcp/backend/cases/forms.py.
  2. A2. Date picking in UI flowszas_test/flows.py:161 steps month by month, at most 120 times, so a 1976 date of birth can never be picked. Jump by year (react-calendar's double-arrow buttons or its decade view), then by month.
  3. A3. Scenario runnerGenerated .zas/test_scenarios.py fails with No module named 'test_fixtures': put .zas/ on sys.path. Also fix the crash on the row-actions shape ('list' object has no attribute 'get').
  4. A4. Cron in platform:scheduleAlready fixed in 94e7703c. Keep it in the re-run checklist.
Phase B: mockup check gate (analyst side, before approval)
  1. B1. Fresh page per screenpreview_probe_worker.open_capture reuses one page, so a crash on screen 5 blanked every screen after it. Load the prototype on a new page for each screen (same browser and context). Verified: on fresh pages detail, admin-dash and admin-cases render fully.
  2. B2. Sample record per screenform and sp still crash on a fresh page, because the capture passes ZAS.store's first row and the imported script expects its own state. The manifest's sample becomes required for record screens of an imported prototype, and the analyst sets it.
  3. B3. Gate the approvalAdd to the readiness check in spec_tools.py (around line 739, "Not ready"): every screen that will be built captures with blank=false and no errors. The analyst fixes the screen or marks it prototype-only. As a backstop, write_prototype_bundle refuses to start a build when a screen to build is blank.
  4. B4. No reference means no passDesign parity reports a blank reference as "no reference" (an internal failure), never as a 0% difference.
Phase C: screen links in the YAML (analyst)
  1. C1. prototype: on pages and detail viewsThe analyst writes pages.<code>.prototype: <screen id> while writing the page. spec_check validates the link instead of inferring it (today's "Maps" column).
  2. C2. Field coverageFor each linked screen, the labels it shows (proto_landmarks.py) must match fields or actions in the spec. A mismatch becomes an analyst question in the chat, before approval.
Phase D: kit from the mockup (build side, automatic gate)
  1. D1. Same interface as the default kitThe agent writes frontend/src/custom/kit/, overriding a subset of the default exports: ui.tsx (Button, Badge, Chip, Panel, StatTile, Tabs, Timeline, FieldGrid, Modal, Drawer…), ZasTable and makeShell. A Vite alias resolves zas/ui to the custom kit, which re-exports defaults for everything it doesn't override. Tokens come from app.design as today.
  2. D2. Kit mapThe agent declares .zas/kit.map.json: each component → mockup screen + CSS selector of a representative instance. The capture crops that element from the mockup.
  3. D3. Kit galleryGallery.tsx (/app/__zas) gains a "mockup kit" mode that renders each overridden component with the mockup's sample content, next to its crop.
  4. D4. Automatic gateDiff each pair. If it's over the threshold (start at 5%), the agent fixes it and the pair is diffed again, up to AGENT_MODE_KIT_ROUNDS (default 3). Remaining gaps go to the internal build report only. The creator sees progress, nothing else.
  5. D5. Drop "theme" in open modeEvery screen is built from kit pieces, so standard list pages use the kit's table and match. Use "rebuild" (slot) only for layouts the standard page can't express, and compose those from kit pieces too. Update references/open-mode.md ("Screens: theme or rebuild") and spec_check.py:1825.
Phase E: build in slices, checked inside the session (both modes)
  1. E1. Slice planspec_check writes .zas/slices.json: slice 0 = shell + kit; slice 1 = the hero record (model, forms, list, create flow, its screens); then its 360; then dashboards and custom pages; then the remaining records. Each slice lists its layer groups and screens.
  2. E2. studio_verify(slice) toolThe build agent calls it after each slice. It runs an incremental bring_up, then verify(only=…) for that slice's groups (verify already takes groups) plus parity for the slice's screens, and returns a short digest. It runs off the SDK pump like the other studio steps.
  3. E3. Build order in SKILL.mdFor each slice: write → verify → fix (at most 3 tries) → next. A slice that won't pass is recorded and the build moves on. Create case is proven in slice 1, minutes into the build.
  4. E4. Final loop staysThe existing post-build loop (studio_build.py:1856) runs once at the end, mainly to catch regressions across slices.
Phase F: failure routing and stop rules
  1. F1. Owner per failureClassify by traceback and path: frames in zas_test/, scripts/ or vendored zas_core/ mean platform; workspace backend/<module> or frontend/src/custom mean app. digest() sends only app failures to the agent. Platform failures go into the run's studio_report.platform_issues for us.
  2. F2. Repeat detectorA failure is identified by check id plus a hash of its message. If the same failure is still there after a fix attempt, it gets no more rounds and is escalated.
  3. F3. No runtime patchingguards.py denies agent writes to backend/zas_core/**, and monkey-patching runtime classes from app code. A report_platform_issue tool replaces workarounds like the one in cases/forms.py.

Risk notes

⚠ Kit coverage: ui.tsx exports about 35 components. The kit overrides only what the mockup shows; the rest falls back to the default and may look off-brand. The kit map should list the fallbacks in the internal report.
⚠ Imported prototypes are arbitrary apps: some screens need state that only a click path creates. If sample isn't enough, allow a short recorded click path per screen; otherwise mark it reference-only.
⚠ Diff noise: dynamic text, fonts and data make pixel diffs flaky. Render the kit with fixed fixture content, wait for fonts, and compare crops of single components rather than whole pages.
⚠ Session time: verifying in the session adds a bring-up (about 30–60 s) plus browser tests per slice. Keep verify incremental (only that slice's groups) and limit tries per slice.
⚠ Threading: studio_verify is called from a tool on the SDK pump, which must not touch the ORM. Route it through the same queue the spec tools use (stream.py) and let the turn loop run the steps.
⚠ Owner classification can be wrong: an app bug can surface inside platform frames. When a platform-classified failure's traceback also contains workspace frames, send it to the agent as well.
