Implementation Plan

Agent Mode — Polished Frontend & Branded Login by Default

Harsh Shah · 2026-09-16 · Plan only, no code changes · branch agent_mode

Overview

Today Agent Mode's "Build with AI" produces a functionally correct Zango app whose UI is whatever appbuilder's prebuilt shell renders: default CRUD lists, a default detail drawer, and the framework's stock login page. The result works but does not look like a product, and the first impression of the generated app is the login screen.

This plan changes the instructions in the Agent Mode skill plugin so that the first version the agent ships is already polished: custom React for the page types that warrant it (detail views, dashboards), and a branded split-screen login page modelled on the au-psp reference implementation.

Scope is documentation/prompt-engineering only — files under backend/src/zango/apps/agent_mode/skill_plugin/. No framework, package or runtime code changes.

Goals / Non-Goals

Goals

  • Detail views of focus entities are full-page custom React routes — never the default side drawer — and any dashboard/report page is custom too.
  • Every generated app ships a branded split-screen login page — always, no exceptions and no toggle.
  • The agent has a correct, copyable auth pattern so custom login never breaks role selection, first-login password reset, or SAML.
  • The agent has an explicit, checkable visual quality bar instead of "make it nice".
  • Phase 1 (analyst) stops steering users away from custom UI, and starts collecting the brand inputs the login page needs.

Non-Goals

  • No changes to @zango-core/crm-framework, appbuilder, crud or any package.
  • No new npm dependencies — the allowlist in STEP 5d stays as-is; the login page must be buildable with what the template ships (inline <style> + inline SVG, exactly as PspLoginCard does).
  • Not a theme editor / App Panel branding UI. This is prompt content only.
  • Not a reuse of the pharma-enterprise-ui skill. That is a separate standalone skill for a different purpose; design-system.md here is domain-neutral and self-contained, and must not import its tokens or its pharma framing.
  • Not attempting pixel-parity with au-psp — it is a pattern reference, not a template to clone.

Target shape — the detail view the agent should produce

This is the heart of "polished": for a focus object — the entity the app is really about, and the one other records point at — a detail page is not a field dump. It is an entity-360: identity header, key facts, then the related records as tables/cards inside tabs, on the same page.

Worked example — Patient. Order, Program, Document and Note all carry a ZForeignKey to Patient. So the Patient detail view shows each of them as its own tab, scoped to that patient — not four separate menu items the user has to visit and filter by hand.

The mechanic (this is what the skill must spell out)

There is no childTables prop. A child table is just another CrudHandler mounted inside a tab, pointed at the child module's own CRUD endpoint with a parent filter appended. The parent module holds no reference to the child beyond that endpoint string:

<CrudHandler
  api_endpoint={`/orders/?patient_uuid=${objectUuid}`}
  headerProps={{ title: 'Orders' }}
/>

Backend side: the child's BaseCrudView narrows its own queryset from that query param — the filter is enforced on the server, never trusted from the client.

Footgun to document verbatim. customTableBody / customMainDetail must be a stable module-scope component reference. An arrow function defined inline in the render creates a new identity each pass, so React unmounts and remounts the whole CRUD subtree → refetch → parent re-render → refetch. The au-psp code carries a 12-line comment about exactly this loop. Any onTotal-style callback must write to a store, never to parent React state.

Which entities get this treatment

TestThen
Other models hold a ZForeignKey to it (≥1 child), and it is a subject the user works on — Patient, Customer, Order, Case, Employee, Program ENTITY-360 custom detail + child tabs
Primary subject but no children yet CUSTOM profile-style detail, no tabs
Referenced by others but never worked on directly — Category, Status, City, Document Type DEFAULT CRUD — a lookup table, not a focus object

Rule of thumb for the agent: read the FK graph. The models with inbound ZForeignKeys that a role actually navigates to are the focus objects. No fixed cap — the agent decides how many qualify from the app's own shape, and justifies the selection in its summary. The test above is the filter; a lookup table never passes it.

Full-page, not a drawer. An entity-360 is a routed page of its own (/app/patients/<uuid>) via enableDetailViewRoute={true} + customMainDetail + customTableBody={NavigateTableBody}. The default side drawer cannot hold child tables, tabs and a timeline — it is the wrong container. Rows navigate; they do not open a drawer.

Required anatomy of an entity-360 page

  1. Header / identity — title, unique ref, avatar or icon, workflow status chip (WorkflowStatus), primary actions, back link.
  2. Key facts strip — 4–8 of the most-consulted fields, from generalDetails.fields. Not all fields.
  3. Overview tab — remaining fields grouped into titled sections, plus summary cards.
  4. One tab per child relation — a scoped CrudHandler, labelled with a count badge.
  5. Timeline / activity where a lifecycle exists.
  6. States — skeleton while loading, empty state per tab, error state. Not optional.

Steps

  1. Add a new reference: references/frontend/entity-360.md
    The detail-view pattern, with the code the server copy currently lacks. Recover the working snippets from the upstream interactive skill rather than re-deriving them:
    • How to decide a focus object from the FK graph (inbound ZForeignKey count + "is it worked on directly").
    • Full-page detail wiring: enableDetailViewRoute + customMainDetail + customTableBody={NavigateTableBody}, and the drawer variant customDrawerDetail.
    • CRITICAL prop-casing trap from upstream: the detail component receives camelCase (generalDetails, objectUuid, workflowDetails) while the raw API is snake_case (general_details). Getting this wrong renders a blank page.
    • Child tables: mount a second CrudHandler per tab at `${childCrudUrl}?${parentParam}=${objectUuid}`. There is no built-in child-table prop — say so explicitly so the agent stops looking for one.
    • CRITICAL stability rule: customTableBody / customMainDetail declared at module scope, never inline — inline identities cause the remount→refetch→re-render loop documented in au-psp.
    • Backend half: the child BaseCrudView filters its own queryset from the parent query param (server-enforced, never client-trusted).
    • The required page anatomy (header → key facts → overview → child tabs → timeline) and the skeleton/empty/error states.
    • A complete copyable <Entity>Detail.tsx skeleton with two child tabs.
  2. Add a new reference: references/frontend/auth-login.md
    The single biggest gap. Contents, derived from PspLoginCard.tsx:
    • Wiring: authConfig={{ customComponents: { LoginPage: MyLogin } }} on ZangoApp — pass the component, not an element.
    • Imports available from @zango-core/crm-framework: PasswordLoginForm, RoleSelection, PasswordResetRequired, authService, getNextParam, getValidRedirectUrl.
    • CRITICAL Drive the flow from PasswordLoginForm's onSuccess, not LoginContext.onLogin (mis-handles the single-role case).
    • The next_step contract and its four response shapes → the extractNextStep helper, verbatim.
    • Handling set_password / password_expiry / first_login → PasswordResetRequired; role_selection → RoleSelection; else redirect via getValidRedirectUrl(next, serverRedirect, '/app').
    • Styling rules for framework-rendered internals (inputs, button[type=submit], stripping the nested card chrome from RoleSelection / PasswordResetRequired).
    • Responsive note: media queries must come last in the CSS string — equal specificity means source order decides.
    • A complete, trimmed skeleton the agent can copy and re-theme.
  3. Add a new reference: references/frontend/design-system.md
    The objective quality bar, so "polished" is checkable rather than aspirational:
    • Token set to declare once per app (brand / brand-600 / text / sub / muted / border / page) and use everywhere — no ad-hoc hex.
    • Pull the palette from the app's theme (useAppContext().theme / initializer --color-brand-500) so the app and login agree.
    • Typography scale, spacing scale, border-radius and elevation conventions.
    • Detail-view anatomy: header/identity block → status → key-fact grid → tabbed or sectioned child entities → activity.
    • Dashboard anatomy: KPI row → primary chart → breakdown table → queue/worklist.
    • Empty, loading (skeleton, not spinner) and error states are required, not optional.
    • Responsive floor: usable at 880px and 480px.
    • Assets constraint: inline SVG + inline <style> only — no new npm packages, no external fonts/CDN.

Risk Notes

Scope creep across entities (turn budget is being raised, so this is about focus, not cost). With no numeric cap, an agent that reads "custom detail view" as "every model" builds twelve mediocre pages instead of three good ones. Mitigation: the focus-object test must read as a filter — a model with no inbound FKs, or one nobody navigates to, fails it — and the summary must name which entities got an entity-360 page and why each remaining model did not. Justification is the brake, in place of a number.
The remount → refetch → re-render loop. The single most likely way a generated detail page ships visibly broken: an inline customTableBody or a child onTotal writing to parent state. It is not obvious from the props and the agent will not infer it. Mitigation: it is called out as CRITICAL in entity-360.md with the module-scope rule stated as code, not prose.
Child scoping enforced only on the client. Appending ?patient_uuid=… is a display filter; if the child BaseCrudView does not narrow its own queryset, any user can edit the URL and read another patient's orders — a tenant-data leak in a healthcare app. Mitigation: entity-360.md pairs every frontend child-table snippet with the backend queryset filter, and STEP 7 requires reporting that the filter is server-side.
Broken auth is worse than an ugly login. A custom LoginPage that mishandles next_step locks every user out. Mitigation: the reference doc leads with the onSuccess/extractNextStep contract and marks it CRITICAL before any styling; STEP 5e requires verifying a multi-role and a first-login user.
Generic AI-looking output. Without a concrete bar, "polished" degrades into purple gradients on every app regardless of domain. Mitigation: design-system.md mandates tokens sourced from the app's own theme, and STEP 5e forbids filler copy — the left panel must state this app's actual domain outcome.
Brand impersonation. Given a real company name the agent may reproduce a real brand's identity. Mitigation: STEP 5e explicitly limits branding to what the requirement spec and theme supply.
Drift from the interactive skill. These edits widen the server/interactive fork. Mitigation: Step 9 (VENDORED.md) — and the two new references are written to be portable back to the interactive skill unchanged.
