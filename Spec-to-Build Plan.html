Spec-to-Build Plan

F1–F4 built · 15 Oct 2026 Branch feat/agent-mode-app-studio-skill Template zango-app 1.1.16 Follows: Preview-to-Spec Plan (part 1)

How an approved spec reaches the build agent so the built app looks like the preview the user approved, custom screens included, at a small fraction of the cost of sending the preview itself.

The plan in three moves
  1. Structure: port the sketch onto the build's own design system. A custom screen's preview sketch already calls a fixed kit (ui.kpis, ui.bars, ui.board…). Add the missing pieces of that kit to zas/ui.tsx, with the same arguments, so the sketch ports to React nearly line by line. The layout then matches by construction instead of by imitation.
  2. Look: a screenshot of every customised screen. Each custom page, 360 tab and 360 panel gets a screenshot, plus one per role or record that draws a different structure. They are files in the workspace that the agent opens when it needs them; they never sit in the prompt.
  3. Check: compare in text first, then look once. The built screen records the same component tree the preview recorded. A script compares the two as text. Then the agent looks at its own screenshot next to the preview's, once per screen.

How others do it

Agents that turn a design into code generally use three kinds of input, and the ones that hold up in real products combine them:

ApproachExamplesFidelity
Screenshot only. The model reads a picture and writes code.screenshot-to-code tools; pasting an image into v0 or a chat modelGood for a one-off mockup. Structure, exact labels, spacing and data rules are guessed from pixels, and they drift.
Structured design data mapped to real components.Figma Dev Mode MCP server (layout, variables, component names as data); Figma Code Connect (a design component ↔ a code component); Builder.io Visual CopilotWhat teams rely on for fidelity. The agent reuses the components the codebase already has, so the result matches by construction.
A visual target and a check loop.Anthropic’s Claude Code guidance: give the target screenshot, let it screenshot its own result, compare, iterateCatches what the structured data misses (overall look, spacing). Costs a few images per screen.

We are in a better position than most: our design data already is code. A sketch calls a fixed component kit, which is the mapping Code Connect tries to recreate for Figma. So we take the hybrid: the sketch for structure, a screenshot for the look, and a text-then-visual check.

The approach

Structure

Sketch → design system

The sketch is ported onto zas/ui.tsx components with the same arguments. Titles, labels, order, icons and tones carry over exactly; demo reads become real data hooks.

Look

Screenshots as the target

Every customised screen, as the role that opens it, on a representative record. Extra shots only where another role or record draws a different structure.

Check

Text parity, then one look

The built screen records its component tree; a script diffs it against the preview’s draw tree. Then one side-by-side look per screen.

From Commit to a checked screen

  1. The user clicks Commit for buildconsole

    The approval gates from part 1 hold: every custom screen has a sketch and a contract.

  2. The platform freezes the approval bundleCelery task

    The preview probe runs each custom screen per role, records its draw tree and takes the screenshots, beside the approved YAML.

  3. spec_check.py points each hole at its bundle filesbuild prepare

    holes.md says: port bundle/screens/<id>/sketch.js, target shot.*.png, check against draws.*.json.

  4. The build agent ports the sketchbuild agent

    Same components, same arguments; a data hook in place of ctx.rows; a server hook when the numbers need the whole table.

  5. Parity check, in textzas_test parity

    The built screen, signed in as each role, emits its component tree; the diff against the draw tree is a few lines of text.

  6. One lookbuild agent

    Its own screenshot next to the preview’s. Fix, and move on to the contract’s acceptance tests.

Extend the design system the build already has

The build agent composes only from src/zas (SKILL.md rule: “Compose from src/zas only. No hex colours”). So the kit goes there, next to the components it already uses, not into a separate library.

Two rules keep the preview and the app from drifting:

  • One stylesheet. Move the kit’s styles into the runtime’s tokens.css (classes such as .zas-bars, .zas-board), and have the preview’s compose() inline that same file instead of its own .ui-* / .d-* copy. Today the two are written separately.
  • Each kit component marks itself. It renders data-zas-kit="bars" and its title on its root, the same way the preview’s recording kit names each call. That is what the parity check reads.

Porting a sketch

The Rejection Analysis sketch, shortened, and its port. The calls map one to one; only the data source changes.

// preview sketch (in the spec)
const rows = ctx.rows('stockist_application').filter(r => r.rejection_count > 0);
return ctx.ui.stack(
  ctx.ui.kpis([{ label: 'Applications rejected at least once', value: rows.length, icon: 'circle-x', tone: 'red' }]),
  ctx.ui.bars('Top 5 rejection reasons', topReasons(rows)),
);
// built slot (frontend/src/custom/slots/RejectionAnalysis.tsx)
export function RejectionAnalysis() {
  const { data, state } = useSlotData('rejection_analysis');   // new hook; the server returns what the sketch computed
  return (
    <Stack state={state}>
      <Kpis items={[{ label: 'Applications rejected at least once', value: data.rejected, icon: 'circle-x', tone: 'red' }]} />
      <Bars title="Top 5 rejection reasons" items={data.top_reasons} />
    </Stack>
  );
}
In the sketchIn the built slot
ctx.rows(entity), ctx.related(entity, via)The role-scoped list API for small lists; a <page>__data hook (already in custom-code.md) when the screen aggregates over the whole table
Counting, grouping, sorting on demo rowsThe same logic in that server hook, returning the shape the sketch passed to the kit
ctx.recordThe record prop a 360 slot already receives
ctx.fmt(row, field), go: 'page:id', ctx.todayThe runtime’s renderers, the kit’s go prop with the same string, the server date
Nothing (sketches draw the happy path)Loading, empty and error states, through state on <Stack> and the contract’s states

What carries over exactly: blocks and their order, titles, labels, icons, tones, column lists, limits and links. What the agent still decides: where the data comes from, the server query, the four states, and the interactions in the contract.

For the Stockist app that is 5–7 images, roughly 300–900 tokens each, and only the ones the agent opens are paid for.

Checking the result

  • Text parity (new zas_test group parity). For each custom screen and each role in the bundle, Playwright opens the built screen, reads every data-zas-kit element in order, and compares kinds, titles, labels, columns and links with the draw tree. Numbers are not compared: the app has its own data. The output is a short diff such as bars "Rejections by city": missing. Like any failing test in the build loop, the agent fixes the slot and runs it again. After 2 fix attempts on a screen, what still differs goes into the build report as a warning naming the screen and the difference; it does not fail the build. This replaces the “preview parity: skipped” lines in testing.md, design-system.md and contracts.md.
  • Hand-written parts. Parts of a sketch drawn with raw markup instead of kit calls have no one-to-one mapping. Parity checks the kit blocks around them, and the agent builds them from the screenshot and the text, with design-system components only.
  • One look per screen. After parity passes, the agent takes one screenshot of its built screen and opens it beside the bundle’s, to judge spacing, density and emphasis. That is two images, about 1.5k tokens.
  • Acceptance tests. As today: the contract’s acceptance lines become tests, now with the same block names to select on.

Risks

RiskMitigation
A sketch writes raw HTML instead of kit calls, so there is nothing to map.Allowed, not refused: some screens need what the kit cannot express. The probe warns the analyst to use kit calls where they fit; the build uses the screenshot and text for those parts, and parity checks the kit blocks around them.
Preview and app styles drift.One stylesheet for both, and kit goldens rendered from both in the same Chromium.
Sketch math over all demo rows does not scale to real data.The porting rule: aggregates move to a server hook that returns the same shape.
Screenshots multiply with roles and records.Shoot variants only where the draw tree’s structure differs; screenshots are opened on demand.
No Playwright on the worker.The bundle still carries the sketches and contracts. Parity and screenshots are skipped, and the build report says so.
Values differ from the preview, which used demo data.Expected: the built app is a real app with real data, and no demo rows are loaded. Parity compares structure only, and the look judges layout, not numbers.
The agent copies the demo-data logic literally.The sketch is a reference for structure; the contract’s data and acceptance define the real behaviour, and tests check them.

Decisions (15 Oct)

QuestionDecision
Load the preview’s demo data into the built app?No. It is a real app; no sample records. Parity compares structure, never values.
Hand-written markup in sketchesAllowed, with a warning to the analyst. The build uses the screenshot and text for those parts.
A parity failureThe agent fixes it in the test loop (up to 2 attempts per screen). Anything left is a warning in the build report, not a failure.
